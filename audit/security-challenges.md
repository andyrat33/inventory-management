**Auditor:** security-auditor · **Date:** 2026-09-07

Both peers largely stayed in their lanes, so there are few direct severity disputes. The notes below cover (1) peer findings whose severity or framing changes under a security lens, (2) findings that gain blast radius when combined with a security finding, (3) items I'd rate more conservatively, and (4) cross-angle duplicates so the synthesis step counts each fix once.

## 1. Peer findings I would re-rate

| Finding                                                                      | Peer severity          | My proposed severity                                              | Rationale                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------- | ---------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **PERF-6** — `/api/orders` returns full unpaginated payload                  | Medium                 | **Medium, but with a security dimension the perf write-up omits** | Perf frames this as network cost. It is also a **data-minimisation / resource-exhaustion** issue: the endpoint has no `limit`, no max response size, and returns `customer` names + full line items. Combined with SEC-1 (no auth) and SEC-2 (any-origin credentialed CORS), any website the user visits can exfiltrate the entire customer order book in one request. The fix (pagination + slim projection + aggregate endpoints) is the same one perf recommends, so keep it at Medium but tag it as serving SEC-1's remediation too — it should not be deprioritised as "just perf."    |
| **PERF-13** — `filter_by_month` uses substring match on `order_date`         | Low                    | **Low (agree) — add input-validation rationale**                  | Perf calls the substring match a "latent correctness risk." No privilege escalation (all data is already public), so Low is correct, but the fix should be "parse and compare date components," not just "prefix match." Ties to my SEC category checklist note on query-param validation.                                                                                                  |

I don't contest perf's "High" on render-cost grounds, but security adds nothing that would raise it.                                                                                                                                             |

## 2. Findings that gain blast radius when combined with a security finding

- **PERF-7** (Dashboard/Spending recompute from raw `/api/orders` in the browser) + **SEC-1** + **SEC-2**: the aggregation-in-browser pattern means the raw customer/order data crosses the network to every view. Moving aggregation server-side (perf's fix) also shrinks the unauthenticated data-exposure surface. Count PERF-7's fix as double-duty.
- **SEC-4** (unbounded request bodies, no rate limiting) is the write-side twin of **PERF-6** (unbounded response, no pagination). One coordinated change — add bounds/pagination/validation + rate limiting at the FastAPI layer — closes both. The synthesis plan should group them.

## 3. Items I'd rate more conservatively than a security-flavoured reading might suggest

- **UX-12** (background action failures swallowed to `console.error`): ux-reviewer's line-50 note anticipates a security "information disclosure" angle. **There is none.** FastAPI returns generic errors (debug off), and the client swallowing them to the console is, if anything, mildly _good_ for security (no error detail surfaced to the user). UX-12 is a pure UX finding (silent data loss) — do not double-list it as a security concern.
- **UX-21** (`alert()` + `console.log` in `Spending.vue` transaction handler): the `console.log` prints transaction vendor/amount to the _user's own_ console. Not a disclosure boundary. Pure UX/consistency issue.
