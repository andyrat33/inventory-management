# Performance Findings — inventory-management

**Summary.** The backend is in reasonable shape for a demo: all JSON is parsed once at module import (`server/mock_data.py:21-42`), not per request, and the in-memory filters are linear, not quadratic. The dataset is tiny (250 orders, 32 inventory items, 9 demand forecasts, 56 transactions), so almost every bottleneck below is _theoretical at current scale_ — it would only bite with real data volume. The exceptions that are **measurable today** are: (1) `Reports.vue` ships `console.log` calls inside template-bound methods that fire on every render (`formatNumber` alone runs 30+ times per render), (2) the `/api/orders` endpoint returns the full ~150 KB unpaginated list and three separate views each fetch it in full, and (3) no route-level code splitting — all 7 views are bundled into the initial payload. The dominant _pattern_ problem on the frontend is derived data computed in template methods instead of `computed()` (Reports, Orders, Demand), which defeats Vue's caching and recomputes on every re-render. `Reports.vue` is also the only view still on the Options API and concentrates most of the findings.

## Notes on measurable vs theoretical

- **Measurable now:** PERF-1 (console spam every render), PERF-6 (150 KB payload × 3 views), PERF-10 (initial bundle includes all views).
- **Pattern issues, low impact at current data size but worth fixing:** PERF-2, PERF-3, PERF-4, PERF-5, PERF-7, PERF-9, PERF-12.
- **Purely theoretical until the dataset grows 10–100×:** PERF-8, PERF-11, PERF-13, PERF-14.
- **Backend is NOT re-reading/re-parsing JSON per request** — verified `server/mock_data.py` loads at import time; the module-level names are reused. No finding there.
- Not a perf issue but noticed in passing: `Dashboard.vue:289` references `<PurchaseOrderModal>` which is not imported or registered in that component (`:305-313` only registers `ProductDetailModal` and `BacklogDetailModal`) — a correctness/runtime concern for the security or UX reviewers to weigh.
